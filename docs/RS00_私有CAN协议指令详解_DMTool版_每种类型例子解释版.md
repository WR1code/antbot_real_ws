## 0. 第一次调试先看这里

### 0.0 CAN 扩展 ID 的分色阅读规则

为了避免把一串 ID 看成一个无法拆分的数字，本文统一采用以下标记：

| 标记 | 字段           | 常见含义                              |
| ---- | -------------- | ------------------------------------- |
| 🟦   | 通信类型       | 查询、运控、使能、停止、读写参数等    |
| ⬜   | 保留字段       | 常规请求帧中通常为`00`              |
| 🟪   | 特殊字段       | 前馈力矩编码、设备发现应答地址等      |
| 🟨   | 新电机 ID      | 仅类型 7 修改 CAN ID 时使用           |
| 🟥   | 状态/结果/故障 | 类型 2 状态字节、类型 17 读参数结果等 |
| 🟩   | 主机 ID        | 本文示例为`0xFD`                    |
| 🟧   | 电机 ID        | 请求中是目标电机，反馈中是来源电机    |

**重要：带颜色符号和竖线的写法只用于理解，不能直接粘贴到 DMTool。**

例如，使能 ID 的两种写法是：

```text
可复制到 DMTool：0300FD7F
只用于理解：    🟦 03（使能） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
```

请求帧与反馈帧的地址方向通常不同：

```text
常规主机请求：🟦 类型 | ⬜/特殊字段 | 🟩 主机 ID | 🟧 目标电机 ID
常规电机反馈：🟦 类型 | 🟥 状态/结果 | 🟧 来源电机 ID | 🟩 主机 ID
设备发现应答：🟦 00   | ⬜ 00       | 🟧 来源电机 ID | 🟪 FE
```

因此，看到 `0300FD7F` 时，应按 `03 | 00 | FD | 7F` 理解；看到 `02807FFD` 时，则应按 `02 | 80 | 7F | FD` 理解，不能沿用请求帧的地址顺序。

### 0.1 DMTool 中必须这样设置

| 项目         | 设置值                                                |
| ------------ | ----------------------------------------------------- |
| 通讯模式     | `CAN`，不是 UART                                    |
| CAN 波特率   | `1 Mbps`，除非电机已改过                            |
| 帧格式       | **扩展帧，29 bit**                              |
| 帧类型       | **数据帧**                                      |
| 数据长度 DLC | `8`                                                 |
| 帧 ID        | 填完整的 29 位扩展 ID，例如`0300FD7F`               |
| Data         | 只填 8 字节 CAN 数据，例如`00 00 00 00 00 00 00 00` |

DMTool 手册说明，点击发送时数据不足会自动补零，但调试 RS00 时仍建议主动填满 8 字节，避免误判。

### 0.2 最安全的首次通信测试

先不要直接发位置、速度或电流控制。推荐按以下顺序确认通信：

```text
1. 查询设备
EXT ID：0000FD7F
ID 拆分：🟦 00（查询设备） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：00 00 00 00 00 00 00 00

2. 正常停止
EXT ID：0400FD7F
ID 拆分：🟦 04（停止/清故障/读版本） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：00 00 00 00 00 00 00 00

3. 读取母线电压 VBUS，index=0x701C
EXT ID：1100FD7F
ID 拆分：🟦 11（读取参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：1C 70 00 00 00 00 00 00
```

确认能收到应答后，再进行使能和运动测试。

### 0.3 首次运动建议

- 先将电机或机构架空，解除外部机械约束。
- 先发停止帧，再切换控制模式。
- 先使用很小的目标速度、电流、位置变化和增益。
- 准备随时发送停止帧：

```text
EXT ID：0400FD7F
ID 拆分：🟦 04（停止/清故障/读版本） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：00 00 00 00 00 00 00 00
```

- 不要把“保存参数”“修改 CAN ID”“修改波特率”“修改协议”放入周期控制循环。

## 1. 必须区分的三层通信

RS00 调试中最容易混淆的是下面三种数据。

| 层级                      | 示例                        | 应该填在哪里                              |
| ------------------------- | --------------------------- | ----------------------------------------- |
| RS00 原始 CAN 扩展 ID     | `1200FD7F`                | DMTool 的“帧 ID”                        |
| RS00 原始 CAN Data        | `05 70 00 00 02 00 00 00` | DMTool 的“数据”                         |
| 灵足官方 USB-CAN 串口封装 | `41 54 ... 0D 0A`         | 仅适用于其串口 AT 协议，不是原始 CAN Data |

### 1.1 原始 CAN 帧

真正出现在 CAN_H、CAN_L 总线上的逻辑帧由以下部分组成：

```text
29 位扩展 ID + DLC + 0~8 字节 Data
```

RS00 私有协议通常使用：

```text
扩展帧 + 数据帧 + DLC=8
```

### 1.2 灵足官方 USB-CAN 的串口封装

RS00 手册给出的官方 USB-CAN 模块串口帧示例：

```text
41 54 90 07 E8 0C 08 05 70 00 00 01 00 00 00 0D 0A
```

其中：

```text
41 54                   串口封装帧头
90 07 E8 0C             被封装后的 CAN ID 字段
08                      CAN 数据长度
05 70 00 00 01 00 00 00 CAN Data
0D 0A                   串口封装帧尾
```

手册示例中，把 `90 07 E8 0C` 作为 32 位数后右移 3 位，可得到原始 CAN ID：

```text
0x9007E80C >> 3 = 0x1200FD01
```

低 3 位还包含 USB-CAN 模块自身的帧属性标志。RS00 手册此处没有完整定义这些标志，因此不要只靠该示例自行推导所有封装规则。

### 1.3 使用 DMTool 时怎么填

DMTool 的 CAN 分析仪本身提供通用 CAN 发送控制台。因此发送 RS00 原始帧时：

```text
帧 ID：1200FD7F
ID 拆分：🟦 12（写入参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
长度：8
数据：05 70 00 00 02 00 00 00
格式：扩展帧
类型：数据帧
```

**不要**在 Data 中加：

```text
41 54
0D 0A
```

也不要把完整的 `1200FD7F` 拆开放进 Data。

## 2. 硬件与通信基础配置

### 2.1 RS00 私有协议基本参数

- CAN 接口：CAN 2.0
- 默认波特率：`1 Mbps`
- 帧格式：29 位扩展帧
- 常规帧类型：数据帧
- 常规 DLC：`8`

### 2.2 官方 USB-CAN 模块拨码说明

RS00 手册说明：

- 拨码开关 1 置于 ON：模块进入 Boot 模式，不能正常连接上位机。
- 拨码开关 2 置于 ON：模块端口接入 `120 Ω` 终端电阻。

注意：开关 2 只表示 USB-CAN 模块这一端接入了一个 120 Ω 电阻。总线另一端是否已经有终端电阻，需要结合电机、转接板和实际接线确认。

### 2.3 DMTool 串口设备

DMTool 手册说明：

- Windows 下通常显示为 `COMx`。
- Linux 下通常显示为 `/dev/ttyACM*` 或 `/dev/ttyUSB*`。
- USB2FDCAN 模块打开串口时，也会打开对应的 libusb 设备端口。

建议连接顺序：

```text
连接 USB-CAN/FDCAN 模块
→ 刷新串口
→ 选择正确设备
→ 打开串口
→ 切换到 CAN 模式
→ 设置 CAN 波特率
→ 接通 CAN 总线与电机电源
```

## 3. 29 位扩展 ID 的结构

### 3.1 基本结构

```text
bit28........bit24 | bit23................bit8 | bit7........bit0
  通信类型 5 bit    |      数据区 2，16 bit      | 目标地址 8 bit
```

可表示为：

```text
EXT_ID = [通信类型][数据区2][目标地址]
          5 bit      16 bit    8 bit
```

组帧公式：

```c
uint32_t ext_id = ((uint32_t)(type & 0x1F) << 24)
                | ((uint32_t)(data2 & 0xFFFF) << 8)
                | ((uint32_t)target_id);
```

### 3.2 常规主机下发帧

除通信类型 1、类型 7 等特殊帧外，大多数主机下发帧使用：

```text
data2 = 0x00MM
MM = 主机 CAN ID
目标地址 = 电机 CAN ID
```

假设：

```text
通信类型 = 3
主机 ID   = FD
电机 ID   = 7F
```

则：

```text
(type << 24)      = 03000000
(data2 << 8)      = 0000FD00
target_id         = 0000007F
--------------------------------
最终扩展 ID       = 0300FD7F
```

### 3.3 主机 ID 和电机 ID 的作用

在常规下发帧中：

```text
bit15~8 = 主机 ID
bit7~0  = 目标电机 ID
```

在电机反馈类型 2 中：

```text
bit15~8 = 当前电机 ID
bit7~0  = 主机 ID
```

也就是说，请求和反馈中两个地址的位置会发生变化。

### 3.4 特殊通信类型

|        类型 | bit23~8 的特殊含义                             |
| ----------: | ---------------------------------------------- |
|           1 | 16 位前馈力矩编码值，不再放主机 ID             |
|           2 | 状态、故障标志和电机 ID                        |
|           7 | 高 8 位是新电机 ID，低 8 位是主机 ID           |
|     17 应答 | 高 8 位是读参数成功/失败标志，低 8 位是电机 ID |
| 24 新版应答 | 状态字段与主动上报应答有关                     |

### 3.5 DMTool 中前导零消失是否有影响

例如：

```text
017FFF7F
```

有些软件会显示为：

```text
17FFF7F
```

只要它被作为十六进制数解析，数值相同。关键是必须选择 **29 位扩展帧**，不能选择标准帧。

## 4. 字节序和数据类型

RS00 私有协议不是统一一种字节序，必须按通信类型区分。

### 4.1 类型 1：16 位字段使用高字节在前

```text
Byte0-1：位置 p_set，MSB 在前
Byte2-3：速度 v_set，MSB 在前
Byte4-5：Kp，MSB 在前
Byte6-7：Kd，MSB 在前
```

例如：

```text
0x8208 → 82 08
0x028F → 02 8F
```

### 4.2 类型 2：反馈量使用高字节在前

```text
Byte0-1：角度
Byte2-3：角速度
Byte4-5：力矩
Byte6-7：温度 × 10
```

例如：

```text
Byte6-7 = 01 2C
0x012C = 300
温度 = 300 / 10 = 30.0 ℃
```

### 4.3 类型 17/18：参数索引和值使用低字节在前

```text
Byte0-1：index，小端
Byte2-3：00 00
Byte4-7：参数值，小端
```

例如索引：

```text
index = 0x701E
Data Byte0-1 = 1E 70
```

### 4.4 IEEE-754 float 小端常用值

| 十进制 float |  32 位十六进制 | RS00 Data 中的 4 字节 |
| -----------: | -------------: | --------------------- |
|      `0.0` | `0x00000000` | `00 00 00 00`       |
|      `0.2` | `0x3E4CCCCD` | `CD CC 4C 3E`       |
|      `0.5` | `0x3F000000` | `00 00 00 3F`       |
|      `1.0` | `0x3F800000` | `00 00 80 3F`       |
|      `2.0` | `0x40000000` | `00 00 00 40`       |
|      `5.0` | `0x40A00000` | `00 00 A0 40`       |
|     `10.0` | `0x41200000` | `00 00 20 41`       |
|     `20.0` | `0x41A00000` | `00 00 A0 41`       |
|     `30.0` | `0x41F00000` | `00 00 F0 41`       |
|     `40.0` | `0x42200000` | `00 00 20 42`       |
|     `-0.5` | `0xBF000000` | `00 00 00 BF`       |
|     `-1.0` | `0xBF800000` | `00 00 80 BF`       |

### 4.5 uint8、uint16、uint32 写入方式

参数类型为 `uint8`：

```text
Byte4 = 参数值
Byte5-7 = 00 00 00
```

参数类型为 `uint16`：

```text
Byte4 = 低字节
Byte5 = 高字节
Byte6-7 = 00 00
```

参数类型为 `uint32`：

```text
Byte4-7 = 32 位整数小端
```

例如 `canTimeout=20000`：

```text
20000 = 0x00004E20
小端 = 20 4E 00 00
```

完整写入帧：

```text
EXT ID：1200FD7F
ID 拆分：🟦 12（写入参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：28 70 00 00 20 4E 00 00
```

### 4.6 类型 21 的 fault/warning 字节序

手册明确给出了：

```text
Byte0-3：fault
Byte4-7：warning
```

但该表没有像类型 17/18 那样明确写出 32 位整数的高低字节顺序。建议在实机调试中通过制造已知故障并抓包确认。不要在没有确认字节序时，仅凭单个字节位置直接判断复杂故障组合。

## 6. 各通信类型详解

## 6.1 类型 0：获取设备 ID

### 请求帧

```text
EXT ID：0000FD7F
ID 拆分：🟦 00（查询设备） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：00 00 00 00 00 00 00 00
```

字段拆解：

```text
type      = 0x00
bit15~8   = 0xFD，主机 ID
bit7~0    = 0x7F，目标电机 ID
```

### 手册应答示例

```text
type      = 0x00
bit15~8   = 当前电机 CAN ID
bit7~0    = 0xFE
Data      = 64 位 MCU 唯一标识符
```

当电机 ID 为 `0x7F` 时，手册表格对应的应答扩展 ID 为：

```text
EXT ID：00007FFE
ID 拆分：🟦 00（设备 ID 应答） | ⬜ 00（保留） | 🟧 7F（来源电机） | 🟪 FE（发现应答地址）
Data  ：8 字节 MCU 唯一标识符
```

注意：手册在类型 0 应答中使用 `0xFE`，并未将请求中的 `0xFD` 原样放回低 8 位。解析设备发现帧时应按手册示例兼容此行为。

### 用途

- 验证总线是否通。
- 查找电机设备。
- 修改 CAN ID 后确认新 ID。
- 类型 7、23、25 的部分应答也引用了类型 0 广播帧。

---

### 6.1.1 完整收发例子：确认一台新电机是否在线

#### 这条消息在说什么

可以把它理解成主机在总线上点名：

```text
主机 0xFD：
“CAN 地址为 0x7F 的电机在吗？请把你的固定身份编号发给我。”
```

#### 主机发送

```text
完整 ID：0000FD7F
字段拆分：🟦 00（获取设备 ID） | ⬜ 00（保留） | 🟩 FD（主机 ID） | 🟧 7F（目标电机 ID）
Data    ：00 00 00 00 00 00 00 00
```

逐段解释：

| 字段     |     数值 | 含义                                |
| -------- | -------: | ----------------------------------- |
| 通信类型 |   `00` | 请求获取设备 ID                     |
| 保留字段 |   `00` | 本指令不使用                        |
| 主机 ID  |   `FD` | 由主机`0xFD` 发起查询             |
| 目标 ID  |   `7F` | 只点名当前 CAN ID 为`0x7F` 的电机 |
| Data     | 全`00` | 本指令没有额外参数                  |

#### 电机返回

下面使用你实机截图中的数据作为例子：

```text
完整 ID：00007FFE
字段拆分：🟦 00（设备查询应答） | ⬜ 00（保留） | 🟧 7F（响应电机 ID） | 🟪 FE（发现应答地址）
Data    ：62 7C 30 02 0C 34 37 04
```

逐段解释：

| 字段        |                        数值 | 含义                             |
| ----------- | --------------------------: | -------------------------------- |
| 通信类型    |                      `00` | 这是查询设备的应答，不是状态反馈 |
| 电机 ID     |                      `7F` | 响应者当前使用 CAN ID`0x7F`    |
| 应答地址    |                      `FE` | 手册为设备发现应答规定的低 8 位  |
| 8 字节 Data | `62 7C 30 02 0C 34 37 04` | MCU 64 位唯一标识符 UID          |

可以记录成：

```text
当前 CAN ID：0x7F
MCU UID     ：62-7C-30-02-0C-34-37-04
```

#### 怎样判断成功

- DMTool 中出现接收帧，而不只是“发送成功”。
- 返回通信类型仍为 `0x00`。
- 返回 ID 中能看到来源电机 ID `0x7F`。
- Data 中有 8 字节 UID。

#### 常见误区

- UID 不是位置、速度、力矩或温度。
- CAN ID 可以修改，UID 通常用于长期识别同一台物理电机。
- 两台新电机都返回 ID `0x7F`，说明它们当前地址相同；应逐台连接并修改为不同 CAN ID。
- 同一个 ID、同一个 UID 重复出现，通常只是同一台电机多次响应或软件保留了多条记录，不能仅凭重复行判断有多台电机。

## 6.2 类型 1：运控模式控制

### 控制律

```text
t_ref = Kd × (v_set - v_actual)
      + Kp × (p_set - p_actual)
      + t_ff
```

内部再把 `t_ref` 换算为目标 Iq，通过电流环驱动电机。

### 字段范围

| 字段      |             物理范围 | 编码位置        | 字节序    |
| --------- | -------------------: | --------------- | --------- |
| `t_ff`  |        `-14~14 Nm` | 扩展 ID bit23~8 | 16 位编码 |
| `p_set` | `-12.57~12.57 rad` | Byte0-1         | 大端      |
| `v_set` |     `-33~33 rad/s` | Byte2-3         | 大端      |
| `Kp`    |            `0~500` | Byte4-5         | 大端      |
| `Kd`    |              `0~5` | Byte6-7         | 大端      |

### 编码和解码

```text
u16 = int((x - xmin) × 65535 / (xmax - xmin))
```

```text
x = u16 × (xmax - xmin) / 65535 + xmin
```

编码前应先将 `x` 限幅到 `[xmin, xmax]`。

手册示例程序使用强制类型转换，因此通常是向零截断，而不是四舍五入。例如中值 `0` 会得到 `0x7FFF`，而不是 `0x8000`。

### 完整组帧

```text
EXT ID：
[type=0x01][t_ff_u16][motor_id]

Data：
[p_u16_MSB p_u16_LSB]
[v_u16_MSB v_u16_LSB]
[kp_u16_MSB kp_u16_LSB]
[kd_u16_MSB kd_u16_LSB]
```

### 绝对位置 0.2 rad 示例

目标：

```text
p_set = 0.2 rad
v_set = 0 rad/s
Kp    = 5
Kd    = 0.5
t_ff  = 0 Nm
```

编码结果：

```text
t_ff 0 Nm   → 0x7FFF
p 0.2 rad   → 0x8208
v 0 rad/s   → 0x7FFF
Kp 5        → 0x028F
Kd 0.5      → 0x1999
```

帧：

```text
EXT ID：017FFF7F
ID 拆分：🟦 01（运控控制） | 🟪 7FFF（前馈力矩编码） | 🟧 7F（目标电机）
Data  ：82 08 7F FF 02 8F 19 99
```

发送前必须先使能：

```text
EXT ID：0300FD7F
ID 拆分：🟦 03（使能） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：00 00 00 00 00 00 00 00
```

### 运控模式的三种典型用法

#### 类速度控制

```text
t_ff=0
p_set=0
Kp=0
v_set=目标速度
Kd>0
```

手册举例：`v_set=1 rad/s`、`Kd=1`，空载时电机会趋向 1 rad/s；负载增大时需要适当增加 Kd。

#### 阻尼模式

```text
t_ff=0
p_set=0
Kp=0
v_set=0
Kd>0
```

外力转动电机时会产生与速度相关的反向阻尼。手册特别提醒：此工况电机可能发电，需要电源具备回馈吸收能力，避免母线过压。

#### 位置保持

```text
t_ff=0
p_set=目标位置
Kp>0
v_set=0
Kd>0
```

- Kp 越大，位置保持作用越强。
- Kd 提供阻尼。
- Kd 过小或为 0 时，电机到达目标位置后可能振荡。

### 重要说明

- `p_set` 是相对机械零位的 **绝对位置**。
- 发送 `p_set=0.2` 表示去到零位附近的 `0.2 rad`，不是“在当前角度上再增加 0.2 rad”。
- 运控帧 ID 的 bit23~8 已被前馈力矩占用，不再携带主机 ID。

### 6.2.1 完整收发例子：让电机保持在机械零位后的 `0.2 rad`

#### 这条消息在说什么

```text
主机：
“请以 0.2 rad 为绝对目标位置，目标速度为 0，
位置刚度 Kp=5、速度阻尼 Kd=0.5、前馈力矩为 0。”
```

这不是“从当前位置再转 0.2 rad”，而是“转到相对于机械零位的 0.2 rad”。

#### 第一步：先使能

```text
完整 ID：0300FD7F
字段拆分：🟦 03（使能） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：00 00 00 00 00 00 00 00
```

#### 第二步：发送运控指令

```text
完整 ID：017FFF7F
字段拆分：🟦 01（运控控制） | 🟪 7FFF（前馈力矩 0 Nm 的编码） | 🟧 7F（目标电机）
Data    ：82 08 | 7F FF | 02 8F | 19 99
           位置     速度      Kp       Kd
```

Data 逐字段解释：

| 字节       |    原始值 | 解码含义              |
| ---------- | --------: | --------------------- |
| Byte0-1    | `82 08` | 目标位置约`0.2 rad` |
| Byte2-3    | `7F FF` | 目标速度约`0 rad/s` |
| Byte4-5    | `02 8F` | `Kp≈5`             |
| Byte6-7    | `19 99` | `Kd≈0.5`           |
| ID bit23~8 |  `7FFF` | 前馈力矩约`0 Nm`    |

#### 预期返回

运控指令的应答是类型 2 状态反馈。下面为便于理解的示意返回，实际数据会随着电机运动而变化：

```text
完整 ID：02807FFD
字段拆分：🟦 02（状态反馈） | 🟥 80（Motor、无故障） | 🟧 7F（来源电机） | 🟩 FD（主机）
Data    ：82 08 | 7F FF | 7F FF | 01 2C
           位置     速度      力矩      温度
```

该示例约表示：

```text
当前位置：0.2 rad
当前速度：0 rad/s
当前力矩：0 Nm
当前温度：30.0 ℃
```

#### 怎样判断成功

- 收到类型 2，而不只是 DMTool 提示“发送成功”。
- 类型 2 的模式状态为 `Motor`。
- 故障位均为 0。
- 反馈位置逐渐接近 `0.2 rad`，速度在到达后接近 0。

#### 常见误区

- 运控类型 1 的 ID 中没有主机 ID，bit23~8 已经用来放前馈力矩。
- `Kp`、`Kd` 不是位置和速度，而是控制增益。
- 第一次测试不应使用很大的 Kp/Kd，也不应在机构卡死时直接使能。

## 6.3 类型 2：电机反馈数据

### 扩展 ID 状态位

```text
bit28~24：0x02
bit23~22：模式状态
           0 = Reset，复位/失能
           1 = Cali，标定
           2 = Motor，运行
bit21：未标定
bit20：堵转过载
bit19：磁编码故障
bit18：过温
bit17：三相电流故障
bit16：欠压
bit15~8：当前电机 CAN ID
bit7~0：主机 CAN ID
```

### 模式状态无故障示例

假设：

```text
模式状态 = Motor = 2
无故障
电机 ID = 7F
主机 ID = FD
```

则：

```text
type                  = 0x02 << 24 = 0x02000000
mode                   = 2 << 22    = 0x00800000
motor_id               = 0x7F << 8 = 0x00007F00
master_id              = 0xFD      = 0x000000FD
------------------------------------------------
反馈 EXT ID                          = 0x02807FFD
```

### Data 布局

| 字节    | 物理量     |                        解码范围 |
| ------- | ---------- | ------------------------------: |
| Byte0-1 | 当前角度   | `0~65535 → -12.57~12.57 rad` |
| Byte2-3 | 当前角速度 |     `0~65535 → -33~33 rad/s` |
| Byte4-5 | 当前力矩   |        `0~65535 → -14~14 Nm` |
| Byte6-7 | 当前温度   |            `uint16 / 10 = ℃` |

前三个 16 位字段均为高字节在前。

### 解码公式

```text
position = pos_u16 × (12.57 - (-12.57)) / 65535 - 12.57
velocity = vel_u16 × (33 - (-33)) / 65535 - 33
torque   = tor_u16 × (14 - (-14)) / 65535 - 14
temp     = temp_u16 / 10.0
```

### 示例反馈

```text
EXT ID：02807FFD
ID 拆分：🟦 02（状态反馈） | 🟥 80（模式/故障状态） | 🟧 7F（来源电机） | 🟩 FD（主机）
Data  ：82 08 7F FF 7F FF 01 2C
```

近似表示：

```text
模式：Motor
电机 ID：0x7F
主机 ID：0xFD
位置：约 0.2 rad
速度：约 0 rad/s
力矩：约 0 Nm
温度：30.0 ℃
```

### 位置范围和记圈说明

手册说明新版类型 2 位置接口使用 `P_MIN=-12.57`、`P_MAX=12.57`，即约 `-4π~4π`，并以周期方式循环，可借此计算圈数。

同时 `zero_sta` 参数又用于选择上电后零点附近的表示范围：

```text
zero_sta=0：0~2π
zero_sta=1：-π~π
```

这两个说明描述的是不同层面的行为：

- 类型 2 的 16 位编码映射范围约为 `-4π~4π`。
- `zero_sta` 影响上电后的零点表示方式。

不同固件的实际回绕行为可能不同，做多圈位置累计时应先抓包验证。

### 6.3.1 完整解析例子：收到一条状态反馈后从哪里开始看

类型 2 是**电机发给主机**的反馈，不是主机需要主动构造的一条运动命令。

#### 示例帧

```text
完整 ID：02807FFD
字段拆分：🟦 02（状态反馈） | 🟥 80（模式/故障状态） | 🟧 7F（来源电机） | 🟩 FD（接收主机）
Data    ：82 08 | 7F FF | 7F FF | 01 2C
           位置     速度      力矩      温度
```

#### 先解析 ID

```text
02 | 80 | 7F | FD
│    │    │    └─ 反馈发给主机 0xFD
│    │    └────── 反馈来自电机 0x7F
│    └─────────── 模式为 Motor，示例中无故障
└──────────────── 通信类型 2
```

`0x80` 的二进制为：

```text
1000 0000
^^
bit23~22 = 10b = 2 = Motor
```

#### 再解析 Data

```text
Byte0-1：82 08 → 位置约 0.2 rad
Byte2-3：7F FF → 速度约 0 rad/s
Byte4-5：7F FF → 力矩约 0 Nm
Byte6-7：01 2C → 0x012C=300 → 30.0 ℃
```

#### 另一例：类型 2 中出现欠压状态位

若模式仍为 Motor，同时 bit16 欠压位置 1，则第二个 ID 字节由 `80` 变为 `81`：

```text
完整 ID：02817FFD
字段拆分：🟦 02（状态反馈） | 🟥 81（Motor + 欠压） | 🟧 7F（来源电机） | 🟩 FD（主机）
```

此时不要只看 Data 中的位置和温度，应先处理欠压问题。

#### 收到类型 2 时的固定阅读顺序

```text
第 1 步：看通信类型是否为 02
第 2 步：看 mode 是 Reset、Cali 还是 Motor
第 3 步：看 bit21~16 是否有故障
第 4 步：确认来源电机 ID
第 5 步：解析位置、速度、力矩、温度
```

#### 常见误区

- `02807FFD` 不能按请求帧的“主机 ID 在前、电机 ID 在后”理解；反馈方向已经交换。
- Data 的前三组 16 位量是大端，不能按参数读写的小端方式组合。
- 类型 2 是实时状态，连续多条 Data 不同是正常现象。

## 6.4 类型 3：电机使能

```text
EXT ID：0300FD7F
ID 拆分：🟦 03（使能） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：00 00 00 00 00 00 00 00
```

应答：类型 2 电机反馈帧。

使能只让电机进入可运行状态，具体运动目标由当前控制模式和后续控制指令决定。

注意：若之前保存了不安全的控制参数或目标值，使能后可能立即出现动作。首次测试应先停止、设置安全模式和小目标，再使能。

### 6.4.1 完整收发例子：使能 ID 为 `0x7F` 的电机

#### 这条消息在说什么

```text
主机 0xFD：
“电机 0x7F，请从复位/失能状态进入可运行状态。”
```

#### 主机发送

```text
完整 ID：0300FD7F
字段拆分：🟦 03（电机使能） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：00 00 00 00 00 00 00 00
```

Data 全 0 的原因是：使能命令的目标、主机和通信类型已经全部放在扩展 ID 中，Data 不再携带额外参数。

#### 预期返回

```text
示意完整 ID：02807FFD
字段拆分    ：🟦 02（状态反馈） | 🟥 80（Motor、无故障） | 🟧 7F（来源电机） | 🟩 FD（主机）
Data        ：当前位置、当前速度、当前力矩、当前温度
```

#### 怎样判断真正使能成功

| 看到的现象              | 能说明什么                    |
| ----------------------- | ----------------------------- |
| DMTool 显示“发送成功” | 只说明 USB-CAN 接受了发送操作 |
| 收到类型 2              | 电机已经对命令作出反馈        |
| mode=`Motor`          | 电机进入运行状态              |
| fault 位全 0            | 未在类型 2 ID 中发现对应故障  |

因此，**“发送成功”不等于“电机已使能”**。

#### 常见误区

- 使能时要修改 DMTool 的“帧 ID”，但不是把电机自身 CAN ID 改掉。
- 从查询帧 `0000FD7F` 切换到使能帧 `0300FD7F`，只是通信类型由 `00` 变为 `03`。
- 使能不等于运动；电机怎样运动由当前模式、已保存参数和后续目标指令决定。

## 6.5 类型 4：停止、清故障和读取版本

类型 4 使用同一个扩展 ID，通过 Data 区区分功能。

### 正常停止

```text
EXT ID：0400FD7F
ID 拆分：🟦 04（停止/清故障/读版本） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：00 00 00 00 00 00 00 00
```

### 停止并清故障

```text
EXT ID：0400FD7F
ID 拆分：🟦 04（停止/清故障/读版本） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：01 00 00 00 00 00 00 00
```

`Byte0=1` 表示清故障。建议先确认故障根因已经消除，再清故障并重新使能。

### 读取版本号

```text
EXT ID：0400FD7F
ID 拆分：🟦 04（停止/清故障/读版本） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：00 C4 00 00 00 00 00 00
```

手册说明版本应答仍使用类型 2 的扩展 ID，Data 开头为：

```text
Byte0 = 00
Byte1 = C4
Byte2 = 56
Byte3~6 = 电机版本号，高位在前
```

手册表格标题只写到 Byte6，但 CAN Data 仍为 8 字节；未明确说明的字节不要自行赋予含义。

---

### 6.5.1 例子 A：正常停止

#### 主机发送

```text
完整 ID：0400FD7F
字段拆分：🟦 04（停止类命令） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：00 00 00 00 00 00 00 00
```

可以理解为：

```text
“电机 0x7F，请停止运行，但不要把故障状态强行清掉。”
```

#### 预期返回

应答为类型 2。无故障且已经退出 Motor 状态时，返回 ID 常表现为 Reset 模式；实际 Data 仍是停止瞬间的位置、速度、力矩和温度。

#### 成功判断

- 收到类型 2。
- 模式由 Motor 转为 Reset/失能状态。
- 反馈速度逐渐接近 0。

### 6.5.2 例子 B：停止并请求清故障

```text
完整 ID：0400FD7F
字段拆分：🟦 04（停止/清故障） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：01 00 00 00 00 00 00 00
           ↑
         Byte0=1，清故障请求
```

可以理解为：

```text
“先停止，并在故障原因已经消失的前提下清除可清除的故障锁存。”
```

注意：清故障不是修复故障。若电压仍低于 12 V、机构仍堵转或电机仍过温，故障可能立刻再次出现。

### 6.5.3 例子 C：读取固件版本

#### 主机发送

```text
完整 ID：0400FD7F
字段拆分：🟦 04（停止类/特殊查询） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：00 C4 00 00 00 00 00 00
              ↑
           Byte1=C4，版本查询标志
```

#### 电机返回的形态

```text
完整 ID：类型 2 的反馈 ID
Data    ：00 C4 56 VV VV VV VV XX
                       └──┬──┘
                     版本原始字节
```

手册明确说明 Byte3~6 为版本号，顺序由高到低；没有明确说明的字节应按原始值保留，不要自行赋义。

#### 常见误区

- 三个操作的扩展 ID 相同，真正区分功能的是 Data。
- `00 00 ...` 是正常停止；`01 00 ...` 是清故障；`00 C4 ...` 是读版本。
- 不要只复制 ID 而忽略 Data，否则可能执行完全不同的功能。

## 6.6 类型 6：设置机械零位

```text
EXT ID：0600FD7F
ID 拆分：🟦 06（设置机械零位） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：01 00 00 00 00 00 00 00
```

含义：将当前位置设置为电机机械零位。

### 模式限制

手册说明：

- CSP 模式可以标零。
- 运控模式可以标零。
- PP 模式会屏蔽标零操作。

新版固件在 CSP 和运控模式下标零时，会同步把期望位置更新为 0，避免因为目标值与当前位置突然产生巨大偏差而立即转动。

### 推荐顺序

```text
1. 发送停止帧
2. 确认机构静止且无机械干涉
3. 确认当前不是 PP 模式
4. 发送标零帧
5. 读取 mechPos 或观察类型 2 反馈验证
6. 如涉及 zero_sta/add_offset，再按需要保存参数
```

### 6.6.1 完整例子：把当前轴位置定义为 `0 rad`

#### 使用场景

假设机构已经手动对准“正前方”，但电机反馈位置不是 0。此时希望以后以该姿态作为机械零位。

#### 第一步：先停止

```text
完整 ID：0400FD7F
Data    ：00 00 00 00 00 00 00 00
```

#### 第二步：发送标零

```text
完整 ID：0600FD7F
字段拆分：🟦 06（设置机械零位） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：01 00 00 00 00 00 00 00
           ↑
         Byte0=1，执行标零
```

可以理解为：

```text
“从现在起，把轴当前所在的机械位置定义为零位。”
```

#### 第三步：验证

可读取只读参数 `mechPos`，index=`0x7019`：

```text
完整 ID：1100FD7F
字段拆分：🟦 11（读取参数） | ⬜ 00 | 🟩 FD | 🟧 7F
Data    ：19 70 00 00 00 00 00 00
```

若读回 Byte4~7 接近：

```text
00 00 00 00  → float 0.0
```

则说明当前位置已接近新的机械零位。

#### 怎样判断成功

- 收到类型 2 应答。
- 再读 `mechPos` 或观察类型 2 位置，位置接近 0。
- 轻微转动后，正负方向与机械定义一致。

#### 常见误区

- 标零不是让电机自动转回旧零位，而是把“当前姿态”重新命名为零位。
- PP 模式会屏蔽标零；应按手册要求在 CSP 或运控模式下执行。
- 标零前必须保证机构静止和安全，避免零点突变造成后续位置指令危险。

## 6.7 类型 7：修改电机 CAN ID

扩展 ID 中：

```text
bit23~16 = 新电机 ID
bit15~8  = 主机 ID
bit7~0   = 当前电机 ID
```

例如把电机从 `0x7F` 改为 `0x01`：

```text
EXT ID：0701FD7F
ID 拆分：🟦 07（修改 CAN ID） | 🟨 01（新电机 ID） | 🟩 FD（主机） | 🟧 7F（当前/旧电机 ID）
Data  ：00 00 00 00 00 00 00 00
```

修改立即生效。后续所有指令必须改用：

```text
目标电机 ID = 0x01
```

例如新的使能帧：

```text
EXT ID：0300FD01
ID 拆分：🟦 03（使能） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 01（目标电机）
Data  ：00 00 00 00 00 00 00 00
```

应答：手册说明为类型 0 广播帧。

### 多电机注意事项

工程上不要让多台具有相同 CAN ID 的电机同时连接后再广播式修改，否则可能出现多台设备同时响应或同时修改。较安全的做法是逐台上电、逐台改 ID、逐台验证。

### 两台新电机都为 `0x7F` 时的逐台改 ID 流程

很多新电机可能都使用同一个默认 CAN ID。若两台电机查询后都返回 `0x7F`，不要让它们同时保持该地址接入同一条总线进行控制。应一次只连接一台。

#### 电机 A：从 `0x7F` 改成 `0x01`

1. 只连接电机 A，查询当前设备：

```text
完整 ID：0000FD7F
ID 拆分：🟦 00（查询设备） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：00 00 00 00 00 00 00 00
```

2. 记录返回的 8 字节 MCU UID，然后修改地址：

```text
完整 ID：0701FD7F
ID 拆分：🟦 07（修改 CAN ID） | 🟨 01（新 ID） | 🟩 FD（主机） | 🟧 7F（当前旧 ID）
Data    ：00 00 00 00 00 00 00 00
```

3. 修改立即生效，随后应使用新目标地址验证：

```text
完整 ID：0000FD01
ID 拆分：🟦 00（查询设备） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 01（目标电机）
Data    ：00 00 00 00 00 00 00 00
```

预计设备发现应答 ID 类似：

```text
完整 ID：000001FE
ID 拆分：🟦 00（设备 ID 应答） | ⬜ 00（保留） | 🟧 01（来源电机） | 🟪 FE（发现应答地址）
Data    ：应与修改前记录的电机 A UID 相同
```

#### 电机 B：从 `0x7F` 改成 `0x02`

断开电机 A，只连接电机 B，然后发送：

```text
完整 ID：0702FD7F
ID 拆分：🟦 07（修改 CAN ID） | 🟨 02（新 ID） | 🟩 FD（主机） | 🟧 7F（当前旧 ID）
Data    ：00 00 00 00 00 00 00 00
```

随后使用 `0000FD02` 查询验证。最终两台电机可以同时接入总线：

```text
使能电机 A：0300FD01
字段拆分  ：🟦 03（使能） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 01（目标电机 A）

使能电机 B：0300FD02
字段拆分  ：🟦 03（使能） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 02（目标电机 B）
```

不要在两台仍然都是 `0x7F` 且同时在线时发送 `0701FD7F` 或 `0702FD7F`，否则两台可能同时修改为同一个新 ID。

### 6.7.1 完整收发例子：把 `0x7F` 改成 `0x01`

#### 这条消息在说什么

```text
主机 0xFD：
“当前地址为 0x7F 的这台电机，请把通信地址改成 0x01。”
```

#### 修改前先查询并记录身份

```text
发送 ID：0000FD7F
返回 ID：00007FFE
返回 UID：例如 62 7C 30 02 0C 34 37 04
```

UID 的作用是验证修改前后仍是同一台物理电机；修改命令本身不需要填写 UID。

#### 发送修改命令

```text
完整 ID：0701FD7F
字段拆分：🟦 07（修改 CAN ID） | 🟨 01（新 ID） | 🟩 FD（主机） | 🟧 7F（当前旧 ID）
Data    ：00 00 00 00 00 00 00 00
```

注意这个 ID 的四段不能交换：

```text
07 | 01 | FD | 7F
命令  新ID  主机  旧ID
```

#### 修改后用新 ID 查询

```text
完整 ID：0000FD01
字段拆分：🟦 00（查询） | ⬜ 00 | 🟩 FD（主机） | 🟧 01（新目标 ID）
Data    ：00 00 00 00 00 00 00 00
```

预计返回：

```text
完整 ID：000001FE
字段拆分：🟦 00（查询应答） | ⬜ 00 | 🟧 01（来源电机） | 🟪 FE
Data    ：应与修改前记录的 UID 相同
```

#### 怎样判断成功

```text
旧地址 0x7F 不再响应
新地址 0x01 可以响应
修改前后 UID 完全相同
```

#### 常见误区

- 修改 CAN ID 与修改通信类型不是一回事。
- 两台电机都为 `0x7F` 时，必须一次只连接一台修改。
- 若两台相同 ID 同时在线发送 `0701FD7F`，两台可能一起改成 `0x01`，仍无法区分。

## 6.8 类型 17：读取单个参数

### 请求格式

```text
EXT ID：1100FD7F
ID 拆分：🟦 11（读取参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：index_L index_H 00 00 00 00 00 00
```

### 读取 loc_kp，index=0x701E

```text
EXT ID：1100FD7F
ID 拆分：🟦 11（读取参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：1E 70 00 00 00 00 00 00
```

### 手册应答示例

```text
EXT ID：11007FFD
ID 拆分：🟦 11（读参数应答） | 🟥 00（结果：成功） | 🟧 7F（来源电机） | 🟩 FD（主机）
Data  ：1E 70 00 00 00 00 F0 41
```

解析：

```text
bit23~16 = 00，读取成功
bit15~8  = 7F，电机 ID
bit7~0   = FD，主机 ID
index    = 0x701E
value    = 00 00 F0 41，小端 float = 30.0
```

### 读取失败标志

手册说明类型 17 应答中：

```text
bit23~16 = 00：读取成功
bit23~16 = 01：读取失败
```

因此不能只看 Data，必须同时解析应答扩展 ID。

---

### 6.8.1 例子 A：读取当前运行模式 `run_mode`

#### 主机发送

`run_mode` 的 index 为 `0x7005`。索引按小端放入 Byte0~1：

```text
完整 ID：1100FD7F
字段拆分：🟦 11（读取参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：05 70 | 00 00 | 00 00 00 00
           index   保留     请求时清零
```

#### 假设电机当前在速度模式，返回

```text
完整 ID：11007FFD
字段拆分：🟦 11（读参数应答） | 🟥 00（读取成功） | 🟧 7F（来源电机） | 🟩 FD（主机）
Data    ：05 70 | 00 00 | 02 00 00 00
           index   保留     run_mode=2
```

解释：

```text
Byte4=02 → uint8 数值 2 → 速度模式
```

### 6.8.2 例子 B：读取母线电压 `VBUS`

`VBUS` 的 index 为 `0x701C`：

```text
发送 ID：1100FD7F
发送 Data：1C 70 00 00 00 00 00 00
```

假设读到 48.0 V，float `48.0` 的小端字节是：

```text
00 00 40 42
```

则应答示意为：

```text
完整 ID：11007FFD
Data    ：1C 70 00 00 00 00 40 42
                         └───────┘
                         float 48.0
```

#### 怎样判断成功

- 应答通信类型为 `0x11`。
- ID 中结果字段为 `00`。
- 应答 index 与请求 index 相同。
- 根据参数表规定的类型解析 Byte4~7。

#### 常见误区

- `1C 70` 表示索引 `0x701C`，不是 `0x1C70`。
- 不能把所有参数都按 float 解码；`run_mode` 是 uint8，`EPScan_time` 是 uint16，`canTimeout` 是 uint32。
- 读取失败时 ID 的结果字段可能是 `01`，此时 Data 即使非零也不能当作有效参数。

## 6.9 类型 18：写入单个参数

### 通用格式

```text
EXT ID：1200FD7F
ID 拆分：🟦 12（写入参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：index_L index_H 00 00 value0 value1 value2 value3
```

其中参数值按参数类型编码：

- `float`：IEEE-754 单精度，小端。
- `uint8`：只用 Byte4。
- `uint16`：Byte4-5 小端。
- `uint32`：Byte4-7 小端。

应答：类型 2 电机反馈帧。

### 写 run_mode=2，速度模式

```text
EXT ID：1200FD7F
ID 拆分：🟦 12（写入参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：05 70 00 00 02 00 00 00
```

### 写 spd_ref=1.0 rad/s

```text
EXT ID：1200FD7F
ID 拆分：🟦 12（写入参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：0A 70 00 00 00 00 80 3F
```

### 写 spd_ref=-1.0 rad/s

```text
EXT ID：1200FD7F
ID 拆分：🟦 12（写入参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：0A 70 00 00 00 00 80 BF
```

### 掉电保存

手册标题明确标注类型 18 为“单个参数写入，掉电丢失”。需要持久化时，再发送类型 22 保存当前可存储变量。

并非所有变量都一定允许持久化，建议：

```text
写参数 → 读回确认 → 类型22保存 → 重新上电 → 再次读回确认
```

### 6.9.1 完整例子：切到速度模式并设置 `1 rad/s`

#### 第一步：停止电机

```text
完整 ID：0400FD7F
Data    ：00 00 00 00 00 00 00 00
```

#### 第二步：写 `run_mode=2`

```text
完整 ID：1200FD7F
字段拆分：🟦 12（写入参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：05 70 | 00 00 | 02 00 00 00
           index   保留     uint8 值 2
```

可以理解为：

```text
“把 0x7005 这个参数写成 2，也就是选择速度模式。”
```

#### 第三步：使能

```text
完整 ID：0300FD7F

```

#### 第四步：写 `spd_ref=1.0 rad/s`

```text
完整 ID：1200FD7F
字段拆分：🟦 12（写入参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：0A 70 | 00 00 | 00 00 80 3F
           index   保留      float 1.0，小端
```

#### 写入时的直接应答

手册规定类型 18 的应答是类型 2，而不是把刚写入的参数原样回显：

```text
示意返回 ID：02807FFD
返回 Data   ：位置 | 速度 | 力矩 | 温度
```

再用类型 17 读回：

```text
读取 run_mode：

读取 spd_ref：
ID   1100FD7F
Data 0A 70 00 00 00 00 00 00
预期值 Byte4~7=00 00 80 3F
```

#### 常见误区

- 类型 18 的 Byte0~1 是参数索引，Byte4~7 才是参数值。
- float 必须使用 IEEE-754 小端；十进制字符 `1.0` 不能直接放入 Data。
- 类型 18 默认掉电丢失。需要保存时使用类型 22，但不要高频保存。
- 运行中不可直接切换控制模式，应先停止。

## 6.10 类型 21：故障反馈

Data 定义：

```text
Byte0-3：fault，非 0 表示故障
Byte4-7：warning
```

### fault 位定义

| 位 |           掩码 | 故障含义                      |
| -: | -------------: | ----------------------------- |
| 16 | `0x00010000` | A 相电流采样过流              |
| 14 | `0x00004000` | 堵转过载算法保护              |
|  9 | `0x00000200` | 位置初始化故障                |
|  8 | `0x00000100` | 硬件识别故障                  |
|  7 | `0x00000080` | 编码器未标定                  |
|  5 | `0x00000020` | C 相电流采样过流              |
|  4 | `0x00000010` | B 相电流采样过流              |
|  3 | `0x00000008` | 过压，电机电压超过 60 V       |
|  2 | `0x00000004` | 欠压，电机电压低于 12 V       |
|  1 | `0x00000002` | 驱动芯片故障                  |
|  0 | `0x00000001` | 电机过温，热敏电阻超过 145 ℃ |

### warning 位定义

```text
warning bit0：电机过温预警，默认阈值 135 ℃
```

### 故障处理建议

```text
1. 立即停止发送运动指令
2. 发送正常停止帧
3. 断开或降低危险负载
4. 解析 fault/warning
5. 排除供电、温度、编码器、堵转等根因
6. 发送 Byte0=1 的类型4清故障帧
7. 再次读取状态，确认故障消失
8. 小参数重新使能测试
```

### 6.10.1 完整理解例子：收到欠压故障

类型 21 是电机主动上报的故障详情，通常不是主机为了让电机运动而发送的控制命令。

#### 逻辑故障值

欠压对应 fault bit2，因此逻辑上的 32 位 fault 值为：

```text
fault = 0x00000004
warning = 0x00000000
```

#### 可能看到的帧结构

按反馈方向，程序通常应准备按以下逻辑拆分 ID：

```text
通信类型 21 | 来源电机 ID | 主机 ID
```

例如来源电机为 `0x7F`、主机为 `0xFD` 时，常见理解形式为：

```text
完整 ID：15007FFD
字段拆分：🟦 15（故障反馈） | ⬜ 00（状态保留） | 🟧 7F（来源电机） | 🟩 FD（主机）
```

但手册类型 21 表格中的示例排列与字段文字存在歧义，因此接收程序应结合实机抓包确认来源/目标地址位置。

#### Data 怎样看

```text
Byte0~3：fault
Byte4~7：warning
```

手册没有明确说明这两个 uint32 在类型 21 中的字节顺序。因此不要把下面某一种排列当作所有固件的绝对规则：

```text
若按常见小端排列：04 00 00 00 | 00 00 00 00
若按大端排列    ：00 00 00 04 | 00 00 00 00
逻辑值均应解释为：fault=0x00000004，欠压
```

#### 与类型 2 互相验证

欠压同时也是类型 2 ID 中的 bit16。若电机仍处于 Motor 状态，可能看到：

```text
类型 2 ID：02817FFD
                    ↑
                  欠压位为 1
```

#### 处理流程例子

```text
1. 发送停止：0400FD7F / 00 00 00 00 00 00 00 00
2. 测量电机端实际电压，而不是只看电源铭牌
3. 检查接头、线径、压降和电源限流
4. 电压恢复后发送清故障：0400FD7F / 01 00 00 00 00 00 00 00
5. 再观察类型 2 和类型 21 是否仍有故障
```

#### 常见误区

- `fault != 0` 才表示存在故障；不能只凭“收到类型 21”就断言某一种具体故障。
- 多个故障位可以同时为 1，应使用按位与逐项判断，不能用等号只匹配一个数值。
- 清故障不能消除真实的欠压、过温、堵转或硬件问题。

## 6.11 类型 22：保存参数

适用于手册标注的固件 `0.0.3.0` 及以后版本：

```text
EXT ID：1600FD7F
ID 拆分：🟦 16（保存参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：01 02 03 04 05 06 07 08
```

作用：保存当前所有可存储变量。

注意：

- 不要周期发送。
- Flash 擦写次数有限。
- 保存前先读回参数确认数值正确。
- 保存后最好重新上电并再次读取验证。

---

### 6.11.1 完整例子：修改位置环 Kp 后永久保存

#### 第一步：写入 `loc_kp=30.0`

`loc_kp` 的 index 为 `0x701E`，float `30.0` 的小端字节为 `00 00 F0 41`：

```text
完整 ID：1200FD7F
字段拆分：🟦 12（写参数） | ⬜ 00 | 🟩 FD | 🟧 7F
Data    ：1E 70 00 00 00 00 F0 41
```

#### 第二步：读回确认

```text
完整 ID：1100FD7F
Data    ：1E 70 00 00 00 00 00 00
```

预期读取结果 Byte4~7 为：

```text
00 00 F0 41 → 30.0
```

#### 第三步：发送保存命令

```text
完整 ID：1600FD7F
字段拆分：🟦 16（保存参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：01 02 03 04 05 06 07 08
```

这里的 `01 02 03 04 05 06 07 08` 是手册规定的固定保存指令数据，不是 8 个待保存参数。

#### 预期返回

应答为类型 2 状态反馈。该反馈表示电机处理了保存请求，但要确认“确实掉电保存”，仍应：

```text
电机断电 → 重新上电 → 再次读取 0x701E → 确认仍为 30.0
```

#### 常见误区

- 类型 22 保存的是当前所有可存储变量，不是只保存最后写的一个参数。
- 收到类型 2 不等于已经验证掉电保持，真正验证需要重新上电读回。
- Flash 有擦写寿命，不要把类型 22 放进毫秒级控制循环。

## 6.12 类型 23：修改 CAN 波特率

重新上电生效。

```text
EXT ID：1700FD7F
ID 拆分：🟦 17（修改波特率） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：01 02 03 04 05 06 F_CMD 00
```

|  F_CMD |     新波特率 |
| -----: | -----------: |
| `01` |   `1 Mbps` |
| `02` | `500 kbps` |
| `03` | `250 kbps` |
| `04` | `125 kbps` |

### 改成 500 kbps

```text
EXT ID：1700FD7F
ID 拆分：🟦 17（修改波特率） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：01 02 03 04 05 06 02 00
```

### 完整操作流程

```text
1. 记录当前电机 ID、主机 ID、当前波特率
2. 在当前波特率下发送类型23
3. 等待应答
4. 电机断电重启
5. DMTool/主控 CAN 接口切换到新波特率
6. 发送类型0查询验证
```

如果重启后通信消失，最常见原因是主机仍停留在旧波特率。

---

### 6.12.1 完整例子：从 `1 Mbps` 改成 `500 kbps`

#### 修改前

```text
电机当前波特率：1 Mbps
DMTool 当前波特率：1 Mbps
电机 CAN ID：0x7F
```

#### 主机发送

```text
完整 ID：1700FD7F
字段拆分：🟦 17（修改波特率） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：01 02 03 04 05 06 02 00
                              ↑
                         F_CMD=02，500 kbps
```

前六个字节是手册规定的固定序列，Byte6 才是波特率选择值。

#### 预期返回

手册说明应答参考类型 0。收到应答后，新波特率并不会立刻在当前上电周期切换；需要重新上电。

#### 重启后的验证

```text
1. 电机断电重启
2. DMTool 改为 500 kbps
3. 仍使用扩展帧、DLC=8
4. 发送查询：0000FD7F / 00 00 00 00 00 00 00 00
5. 收到 00007FFE 和原 UID，说明新波特率通信成功
```

#### 常见误区

- 只重启电机、不修改 DMTool 波特率，会表现为完全收不到帧。
- Byte6=`02` 是 500 kbps，不是把十进制 `500000` 放进 Data。
- 两台挂在同一总线的设备必须使用相同总线波特率；不要只修改其中一台后继续混接。

## 6.13 类型 24：主动上报开关

适用于手册标注的固件 `0.0.3.0` 及以后版本。

```text
EXT ID：1800FD7F
ID 拆分：🟦 18（主动上报开关） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：01 02 03 04 05 06 F_CMD 00
```

```text
F_CMD=00：关闭主动上报，默认
F_CMD=01：开启主动上报
```

开启：

```text
EXT ID：1800FD7F
ID 拆分：🟦 18（主动上报开关） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：01 02 03 04 05 06 01 00
```

关闭：

```text
EXT ID：1800FD7F
ID 拆分：🟦 18（主动上报开关） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：01 02 03 04 05 06 00 00
```

开启后默认约每 `10 ms` 上报一次类型 2 反馈。

### 修改主动上报周期

参数：

```text
index = 0x7026
name  = EPScan_time
类型  = uint16
默认  = 1
```

手册定义：

```text
1 → 10 ms
每增加 1 → 增加 5 ms
```

当 `n>=1` 时，可整理为：

```text
周期 ms = 10 + (n - 1) × 5
```

例如设为 `20 ms`：

```text
n = 3
```

写入帧：

```text
EXT ID：1200FD7F
ID 拆分：🟦 12（写入参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：26 70 00 00 03 00 00 00
```

手册没有明确 `EPScan_time=0` 的行为，不建议使用未定义值。

### 固件版本差异

手册写明：

- `0.0.3.2` 及以前，类型 24 的应答为类型 2。
- 新版本表格给出的应答通信类型为 `0x18`。

因此程序不要只接受一种固定应答类型，应结合固件版本或同时兼容两种形式。

---

### 6.13.1 完整例子：开启每约 `10 ms` 一次的主动反馈

#### 主机发送开启命令

```text
完整 ID：1800FD7F
字段拆分：🟦 18（主动上报开关） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：01 02 03 04 05 06 01 00
                              ↑
                         F_CMD=01，开启
```

可以理解为：

```text
“电机 0x7F，不用等我每次询问，请按设定周期持续上报状态。”
```

#### 开启后 DMTool 中可能看到

```text
时间 T0：发送 1800FD7F
时间 T1：收到类型 2 或类型 24 应答（取决于固件版本）
时间 T2：收到一条状态数据
时间 T3：约 10 ms 后又收到一条状态数据
时间 T4：继续周期出现
```

状态 Data 仍按位置、速度、力矩、温度解析。

#### 关闭主动上报

```text
完整 ID：1800FD7F
Data    ：01 02 03 04 05 06 00 00
                              ↑
                         F_CMD=00，关闭
```

关闭成功后，周期帧应停止；由使能、写参数等命令触发的被动反馈仍可能继续出现。

#### 怎样判断开启成功

- 不再点击发送时，接收区仍连续出现周期反馈。
- 相邻帧时间间隔大致接近设定周期。
- 来源电机 ID 正确。
- 固件较老时应答可能是类型 2，较新固件可能为类型 24。

#### 常见误区

- 主动上报不是“自动控制电机”，只是自动发送状态。
- 多台电机都以 10 ms 上报会增加总线负载，应合理设置周期。
- `EPScan_time=3` 对应 20 ms，不是 30 ms：`10+(3-1)×5=20 ms`。

## 6.14 类型 25：修改通信协议

重新上电生效。

```text
EXT ID：1900FD7F
ID 拆分：🟦 19（修改协议） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：01 02 03 04 05 06 F_CMD 00
```

|  F_CMD | 协议                |
| -----: | ------------------- |
| `00` | RS00 私有协议，默认 |
| `01` | CANopen             |
| `02` | MIT                 |

### 切换到 CANopen

```text
EXT ID：1900FD7F
ID 拆分：🟦 19（修改协议） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：01 02 03 04 05 06 01 00
```

### 切换到 MIT

```text
EXT ID：1900FD7F
ID 拆分：🟦 19（修改协议） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：01 02 03 04 05 06 02 00
```

手册说明，切换电机协议后还需要配合 CAN 盒执行对应协议切换操作：

- CANopen 使用对应扩展帧协议切换帧。
- MIT 使用对应标准帧指令。

一旦切到其他协议，本文的私有协议帧将不再按原方式生效。修改前务必记录原协议和恢复方法。

---

### 6.14.1 完整例子：从私有协议切换到 CANopen

#### 修改前必须记录

```text
当前协议：RS00 私有协议
当前波特率：例如 1 Mbps
当前 CAN ID：0x7F
当前 MCU UID：记录查询得到的 8 字节
```

#### 主机发送

```text
完整 ID：1900FD7F
字段拆分：🟦 19（修改协议） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data    ：01 02 03 04 05 06 01 00
                              ↑
                         F_CMD=01，CANopen
```

切到 MIT 时，把 Byte6 改成 `02`：

```text
01 02 03 04 05 06 02 00
```

恢复/保持私有协议时，F_CMD 为 `00`。

#### 预期返回和生效时机

手册说明应答参考类型 0，协议在重新上电后生效。

```text
发送类型 25 → 等待应答 → 电机断电重启 → CAN 盒切换到对应协议
```

#### 切换后会发生什么

切到 CANopen 或 MIT 后，本文中的私有协议帧，例如：

```text
0300FD7F
1200FD7F
1100FD7F
```

将不再按原私有协议含义工作。此时必须使用对应协议的帧和工具配置。

#### 怎样判断成功

- 修改前收到手册规定的应答。
- 重启后，使用目标协议能识别和控制电机。
- 原私有协议查询不再按原方式响应，是协议已经变化的可能表现之一，但不能仅凭“收不到”排除波特率、接线等问题。

#### 常见误区

- 修改协议不是修改 CAN ID，两者是独立设置。
- 只修改电机、不切换 CAN 盒/上位机协议，会导致通信失败。
- 在没有准备对应协议恢复方法前，不应随意切换。

### 7.1 读取 VBUS

```text
EXT ID：1100FD7F
ID 拆分：🟦 11（读取参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：1C 70 00 00 00 00 00 00
```

应答 Byte4-7 为小端 float，单位 V。

### 7.2 设置 CAN 超时保护为 100 ms

DMTool 手册进一步说明 CAN Timeout 的一个计数周期为 `50 μs`，且只在电机使能时生效。

```text
100 ms / 50 μs = 2000
2000 = 0x000007D0
小端 = D0 07 00 00
```

写入：

```text
EXT ID：1200FD7F
ID 拆分：🟦 12（写入参数） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data  ：28 70 00 00 D0 07 00 00
```

若需要掉电保持，再发送类型 22。

常用换算：

| 目标超时 | canTimeout 计数值 | 小端字节        |
| -------: | ----------------: | --------------- |
|   100 ms |          `2000` | `D0 07 00 00` |
|   500 ms |         `10000` | `10 27 00 00` |
|      1 s |         `20000` | `20 4E 00 00` |

```text
2. 保存

```

重新上电后再读 `0x7029` 验证。

### 7.4 add_offset 的含义

手册示例含义可整理为：

- 在当前物理位置标零。
- 再设置 `add_offset=1 rad`。
- 重启后坐标零点相对原标零点发生 1 rad 的偏置。

该参数会改变软件坐标和真实机械位置的对应关系。设置前应记录原值并保证机构没有限位风险。

### 7.5 damper 的含义

手册描述的是“未上电时快速反驱产生阻尼”的保护功能，用于降低外部高速旋转造成浪涌的风险。

```text
damper=1：取消该反驱保护
```

因此 `damper=1` 不等于“增加阻尼”，而是取消手册所说的关机反驱保护。修改前应确认系统有能力处理回馈能量。

### 7.6 iq_test 和齿槽补偿

手册给出的流程为：

```text
1. iq_test=1
2. 重启电机，初始化时间会延长，初始基准更精确
3. 电机空载
4. 在上位机执行齿槽标定
5. 标定成功后确认 max_alve 非 0
6. 设置 alveolous_open=1
7. 在运控模式下生效
```

这些操作属于标定流程，不应在普通运行控制中随意执行。

### 7.7 PP 减速度参数的限制

手册说明：

- `dcc_set` 的 index 是 `0x702E`。
- 需要把 `acc_stutus` 设为 1，才可把 PP 加速度和减速度分开。
- `acc_stutus=0` 时，`acc_set` 同时代表加速和减速。

但本版私有协议参数索引表 **没有给出 `acc_stutus` 的 index**。因此不能只依据本手册构造其类型 18 写入帧，必须通过新版手册、官方代码或实机参数表确认。

## 8. 控制模式完整指令流程

手册首页强调：**电机运行时不可直接切换控制方式。**

严格按手册整理的通用模式切换流程为：

```text
停止 → 写 run_mode → 使能 → 写限制参数 → 写目标指令
```

其中电流模式没有单独的限制参数步骤，直接在使能后写 `iq_ref`。

工程建议：由于使能发生在限制参数写入之前，首次测试应保证上一次保存或保留的参数也是安全值，并把新的目标值设得很小。如果实测确认你的固件在失能状态下可以可靠接受限制参数，也可先写安全限制再使能，但这属于工程优化，不是手册给出的标准顺序。

## 9.6 DMTool 分析仪每一列到底是什么意思

DMTool 的分析仪会把**主机发出的帧**和**总线上接收到的帧**放在同一张表里。看到一行数据时，先不要急着解析 8 字节 Data，应依次看：

```text
状态 → ID → 数据长度 → Data
```

各列含义如下：

| 列名     | 在 RS00 调试中的含义         | 容易误解的地方                                                                   |
| -------- | ---------------------------- | -------------------------------------------------------------------------------- |
| 序号     | 当前分析仪列表中的记录编号   | 不代表 CAN 指令编号，也不一定能单独用于判断请求和应答关系                        |
| 时间戳   | USB-CAN/分析仪记录该帧的时间 | 一发一收可能处于同一个时间刻度；分析仪排序变化后，序号也不一定严格按时间排列     |
| 帧类型   | 数据帧或远程帧               | RS00 私有协议正常使用**数据帧**                                            |
| 帧格式   | 标准帧或扩展帧               | RS00 必须是**29 位扩展帧**                                                 |
| CAN 类型 | 当前通道工作在 CAN 模式      | 不是通信类型 0、2、3；RS00 的通信类型在扩展 ID 的 bit28~24 中                    |
| ID       | 完整的 CAN 扩展 ID           | **不是单独的电机 ID**；里面同时编码了通信类型、状态/主机 ID、电机 ID等信息 |
| 状态     | `发送成功` 或 `接收成功` | `发送成功`只说明 USB-CAN 已把帧发到总线上，不等于电机已经执行成功              |
| 数据长度 | DLC                          | RS00 私有协议通常为`8`                                                         |
| 数据内容 | CAN Data Byte0~Byte7         | 不同通信类型的含义不同，不能统一按一种格式解析                                   |

### 9.6.1 “发送成功”不等于“电机执行成功”

DMTool 出现：

```text
状态：发送成功
```

只能确认：

```text
电脑 → USB-CAN → CAN 总线
```

这一段发送流程没有被软件判定为失败。它**不能单独证明**：

- 电机已经收到；
- 电机 ID 填对；
- 电机已经使能；
- 参数已经写入；
- 电机已经按目标运动。

判断电机是否真的响应，需要继续寻找对应的**接收成功**帧，并解析它的 ID 和 Data。

## 9.6.2 如何把一条发送帧和一条返回帧配成一对

建议按以下四步判断：

```text
第 1 步：看发送帧 ID 的通信类型
第 2 步：查该通信类型规定的应答类型
第 3 步：在相近时间戳附近找“接收成功”帧
第 4 步：解析返回 ID 和 Data，判断状态/数值是否符合预期
```

不能简单要求“发送 ID 和接收 ID 完全相同”。RS00 中很多命令的应答 ID 会改变：

```text
查询设备：发送类型 0 → 返回类型 0，但地址字段改变
使能电机：发送类型 3 → 返回类型 2
停止电机：发送类型 4 → 返回类型 2
参数读取：发送类型 17 → 返回类型 17
参数写入：发送类型 18 → 返回类型 2
```

另外，开启主动上报后，电机会周期发送类型 2 状态帧。这些帧可能并不是对某一条发送命令的一一应答，所以应结合时间戳、通信类型和当前操作判断。

## 9.6.3 你当前截图中的五行记录逐行是什么意思

截图里出现了两种帧：

```text
发送：ID 0xFD7F，Data 00 00 00 00 00 00 00 00
接收：ID 0x7FFE，Data 62 7C 30 02 0C 34 37 04
```

DMTool 省略了 ID 左侧的前导零，因此完整写法是：

```text
0xFD7F → 0x0000FD7F
0x7FFE → 0x00007FFE
```

### A. 发送行：`0x0000FD7F`

```text
完整扩展 ID：00 00 FD 7F
               │ │  │  └─ 目标电机 CAN ID = 0x7F
               │ │  └──── 主机 CAN ID = 0xFD
               └─┴─────── 通信类型 = 0x00，获取设备 ID

Data：00 00 00 00 00 00 00 00
```

这条发送帧的意思是：

> 主机 `0xFD` 向 CAN ID 为 `0x7F` 的电机发送“获取设备 ID/MCU 唯一标识符”请求。

这里 8 字节全零只是该查询命令规定的请求数据，**不代表位置为 0、速度为 0，也不是停止命令**。

### B. 接收行：`0x00007FFE`

```text
完整扩展 ID：00 00 7F FE
               │ │  │  └─ 设备发现应答固定地址字段 = 0xFE
               │ │  └──── 响应电机 CAN ID = 0x7F
               └─┴─────── 通信类型 = 0x00，获取设备 ID 应答

Data：62 7C 30 02 0C 34 37 04
```

这条接收帧的意思是：

> CAN ID 为 `0x7F` 的电机已经响应，返回了 MCU 的 64 位唯一标识符。

建议按原始字节记录为：

```text
UID 字节序列：62-7C-30-02-0C-34-37-04
显示形式：    0x627C30020C343704
```

除非后续厂商接口明确要求反转字节，否则保存和比对 UID 时应以分析仪显示的原始 8 字节顺序为准。

### C. 为什么同样的返回出现了多次

截图中多次收到：

```text
ID   0x7FFE
Data 62 7C 30 02 0C 34 37 04
```

这表示同一台电机对查询命令进行了多次响应，或者分析仪中保留了此前的查询记录。因为返回的电机 ID 和 UID 完全相同，所以这些记录指向的是**同一台电机**，不是三台不同电机。

在你的截图中，时间戳非常接近的发送行和接收行可以视为一组查询-应答。不要仅凭“序号相邻”配对，应优先看时间戳和通信类型。

### D. 这张截图现在能确认什么

可以确认：

```text
[确认] USB-CAN 能发送
[确认] 总线能接收电机应答
[确认] 扩展帧设置正确
[确认] 当前电机 CAN ID = 0x7F
[确认] 电机 MCU UID = 62 7C 30 02 0C 34 37 04
```

尚不能确认：

```text
[不能确认] 电机已经使能
[不能确认] 电机处于 Motor 模式
[不能确认] 当前角度、速度、力矩和温度
[不能确认] 电机没有故障
```

原因是当前返回的是**类型 0 设备发现帧**，不是类型 2 电机状态反馈帧。

## 9.6.4 使能命令发送后，应该怎样看返回帧

### 发送使能

```text
ID   ：0300FD7F
ID 拆分：🟦 03（使能） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data ：00 00 00 00 00 00 00 00
```

发送 ID 拆解：

```text
03 | 00FD | 7F
│     │      └─ 目标电机 ID = 0x7F
│     └──────── 主机 ID = 0xFD
└────────────── 通信类型 3：电机使能
```

### 预期返回

手册规定，类型 3 使能命令返回**类型 2 电机反馈帧**。返回 ID 不是固定只看一个数，因为其中包含模式状态和故障位。

无故障并进入 Motor 模式时，典型扩展 ID 为：

```text
0x02807FFD
```

拆解如下：

```text
02 | 80 | 7F | FD
│    │    │    └─ 主机 ID = 0xFD
│    │    └────── 当前电机 ID = 0x7F
│    └─────────── 模式状态 = 2（Motor），故障位全 0
└──────────────── 通信类型 2：电机反馈数据
```

判断使能结果时，至少要检查：

```text
通信类型 == 2
模式状态   == 2（Motor）
故障位     == 0
电机 ID    == 0x7F
主机 ID    == 0xFD
```

仅看到 DMTool 的“发送成功”，还不能认为使能成功。真正的“使能成功”依据是返回类型 2，且模式状态进入 `Motor`，同时没有危险故障位。

### 类型 2 返回 ID 的位解析

```text
type         = (ID >> 24) & 0x1F
mode         = (ID >> 22) & 0x03
not_calibrated = (ID >> 21) & 0x01
stall_fault    = (ID >> 20) & 0x01
encoder_fault  = (ID >> 19) & 0x01
over_temp      = (ID >> 18) & 0x01
phase_current_fault = (ID >> 17) & 0x01
under_voltage  = (ID >> 16) & 0x01
motor_id     = (ID >> 8)  & 0xFF
master_id    = ID & 0xFF
```

模式字段：

|  mode | 含义             | 调试判断                           |
| ----: | ---------------- | ---------------------------------- |
| `0` | Reset，复位/失能 | 没有进入正常运行状态               |
| `1` | Cali，标定       | 正在标定，不能按正常运动状态理解   |
| `2` | Motor，运行      | 已进入运行状态，还需继续检查故障位 |
| `3` | 手册未定义       | 不应自行猜测，记录完整帧并核对固件 |

### 类型 2 Data 的含义

```text
Byte0 Byte1：当前角度原始值，高字节在前
Byte2 Byte3：当前角速度原始值，高字节在前
Byte4 Byte5：当前力矩原始值，高字节在前
Byte6 Byte7：当前温度×10，高字节在前
```

先拼成 16 位无符号数：

```text
pos_raw  = (Byte0 << 8) | Byte1
vel_raw  = (Byte2 << 8) | Byte3
tor_raw  = (Byte4 << 8) | Byte5
temp_raw = (Byte6 << 8) | Byte7
```

再换算为物理量：

```text
位置 rad   = pos_raw × 25.14 / 65535 - 12.57
速度 rad/s = vel_raw × 66.00 / 65535 - 33.00
力矩 Nm    = tor_raw × 28.00 / 65535 - 14.00
温度 ℃     = temp_raw / 10.0
```

示例：

```text
返回 ID：02807FFD
ID 拆分：🟦 02（状态反馈） | 🟥 80（模式/故障状态） | 🟧 7F（来源电机） | 🟩 FD（主机）
返回 Data：82 08 7F FF 7F FF 01 2C
```

约表示：

```text
通信类型：2，状态反馈
模式：Motor，已进入运行状态
故障：无
电机 ID：0x7F
主机 ID：0xFD
位置：约 0.2 rad
速度：约 0 rad/s
力矩：约 0 Nm
温度：30.0 ℃
```

## 9.6.5 常用命令的“发送 → 返回 → 如何判断”对照表

以下仍假设电机 ID=`0x7F`、主机 ID=`0xFD`。

| 操作          | 主机发送     | 发送 Data 的意义                | 正常返回                        | 返回 Data 的意义                     | 如何判断成功                                              |
| ------------- | ------------ | ------------------------------- | ------------------------------- | ------------------------------------ | --------------------------------------------------------- |
| 查询设备      | `0000FD7F` | 8 字节全零，仅表示查询请求      | 类型 0，如`00007FFE`          | 8 字节 MCU UID                       | 收到类型 0，返回电机 ID 正确且 UID 非全零                 |
| 使能          | `0300FD7F` | 8 字节全零，使能命令无额外参数  | 类型 2                          | 位置、速度、力矩、温度               | mode=Motor，故障位为 0                                    |
| 正常停止      | `0400FD7F` | Byte0=0，正常停止               | 类型 2                          | 停止后的状态量                       | mode 不再是 Motor，速度逐步接近 0；具体状态以实机固件为准 |
| 停止并清故障  | `0400FD7F` | Byte0=1，停止并请求清故障       | 类型 2                          | 清故障后的状态量                     | 故障位消失；若根因仍存在，故障可能立即再次出现            |
| 设置机械零位  | `0600FD7F` | Byte0=1，设置当前位置为机械零位 | 类型 2                          | 标零后的状态量                       | 再读取`mechPos` 或观察位置反馈验证，不只看“发送成功”  |
| 读取参数      | `1100FD7F` | Byte0-1 为参数 index，小端      | 类型 17                         | Byte0-1 回显 index，Byte4-7 为参数值 | 返回 index 与请求一致，读取状态为成功，再按参数类型解码   |
| 写入参数      | `1200FD7F` | Byte0-1=index，Byte4-7=待写值   | 类型 2                          | 当前电机状态，不会原样回显写入值     | 建议再用类型 17 读回同一参数确认                          |
| 保存参数      | `1600FD7F` | 固定`01 02 03 04 05 06 07 08` | 类型 2                          | 当前状态                             | 收到响应后重启，再读回参数验证持久化                      |
| 修改波特率    | `1700FD7F` | Byte6 为波特率命令              | 类型 0                          | 设备应答                             | 断电重启后，主机切到新波特率，再查询设备                  |
| 开/关主动上报 | `1800FD7F` | Byte6=1 开，Byte6=0 关          | 旧固件类型 2；新固件可能类型 24 | 状态数据                             | 开启后观察是否按周期出现反馈；需兼容固件差异              |
| 修改协议      | `1900FD7F` | Byte6 选择私有/CANopen/MIT      | 类型 0                          | 设备应答                             | 重启后按新协议重新建立通信                                |

### 特别注意：类型 18 写参数的返回不等于“值已经核对正确”

例如发送：

```text
ID   1200FD7F
Data 05 70 00 00 02 00 00 00
```

含义是将：

```text
index 0x7005，run_mode
写为 uint8 数值 2，速度模式
```

电机正常返回的是类型 2 状态帧，而不是把 `02 00 00 00` 原样回显。因此更稳妥的验证流程是：

```text
1. 发送类型 18 写入
2. 确认收到类型 2 响应
3. 再发送类型 17 读取 index 0x7005
4. 确认返回 Byte4 = 02
```

这一步属于调试验证建议，可避免“总线发送成功，但参数值、数据类型或 index 实际写错”的情况。

## 9.6.6 收到一条陌生帧时的固定解析模板

以后可以按以下模板记录并分析：

```text
方向：发送 / 接收
完整扩展 ID：0x________
Data：__ __ __ __ __ __ __ __

1. 通信类型 = (ID >> 24) & 0x1F = 0x__
2. 查通信类型表，确定 ID 中间 16 位的含义
3. 查该类型的 Byte0~Byte7 布局
4. 按该类型规定的大端/小端拼接数据
5. 换算物理量或参数值
6. 对照预期应答，判断是否真正执行成功
```

最重要的规则是：

> **先根据 ID 判断通信类型，再决定 Data 怎么解析。不能只看 8 字节数据，也不能把所有返回帧都当成位置、速度、力矩、温度。**

## 9.7 连续发送注意事项

DMTool 支持定时连续发送，但：

- 类型 22 保存参数不能连续发送。
- 类型 7 改 ID 不能连续发送。
- 类型 23 改波特率不能连续发送。
- 类型 25 改协议不能连续发送。
- 类型 6 标零不能连续发送。
- 运控模式类型 1 可以周期发送，但应先低频、小参数测试。
- 速度/位置目标可按控制需求更新，但应设置合理 CAN 超时保护。

## 10. 收不到反馈时按此顺序排查

### 10.1 帧格式错误

最常见错误：选择了标准帧。

必须是：

```text
29 bit 扩展帧 + 数据帧
```

### 10.2 波特率错误

RS00 默认：

```text
1 Mbps
```

如果曾发送类型 23 并重启，电机可能已经切换到 500K、250K 或 125K。

### 10.3 UART/CAN 模式错误

DMTool 打开串口后，还要把通讯模式切换到 CAN。

### 10.4 ID 填错

必须区分：

```text
帧 ID      = 完整 29 位 ID，例如 0300FD7F
电机 ID    = 完整 ID 的低 8 位 7F
主机 ID    = 常规下发帧中的 bit15~8，即 FD
```

### 10.5 把串口封装当作 CAN Data

错误示例：

```text
Data = 41 54 03 00 FD 7F ...
```

正确做法：

```text
帧 ID = 0300FD7F
ID 拆分：🟦 03（使能） | ⬜ 00（保留） | 🟩 FD（主机） | 🟧 7F（目标电机）
Data   = 00 00 00 00 00 00 00 00
```

### 10.6 DLC 不正确

RS00 手册示例均按 8 字节数据区组织，建议固定 DLC=8。

### 10.7 终端电阻或线序问题

确认：

- CAN_H 对 CAN_H。
- CAN_L 对 CAN_L。
- 总线两端终端电阻合理。
- 官方 USB-CAN 模块开关 1 不在 Boot 模式。
- 需要时开关 2 接入 120 Ω。

### 10.8 电机协议已经被切换

若电机被改成 CANopen 或 MIT，私有协议帧不会按本文方式响应。需要先确认当前协议。

### 10.9 修改 ID 后仍使用旧 ID

类型 7 修改立即生效。例如从 `0x7F` 改为 `0x01` 后：

```text
错误：0300FD7F
正确：0300FD01
```

### 10.10 电机处于故障或未标定状态

查看类型 2 扩展 ID 的 fault bits，以及类型 21 的 fault/warning 数据。

## 11. C 语言组帧与解析参考

以下代码按手册中的范围和字节序整理，可用于 STM32/GD32 等主控。发送接口和 CAN 驱动部分需根据你的平台补充。

```c
#include <stdint.h>
#include <string.h>

#define RS_P_MIN  (-12.57f)
#define RS_P_MAX  ( 12.57f)
#define RS_V_MIN  (-33.0f)
#define RS_V_MAX  ( 33.0f)
#define RS_KP_MIN (  0.0f)
#define RS_KP_MAX (500.0f)
#define RS_KD_MIN (  0.0f)
#define RS_KD_MAX (  5.0f)
#define RS_T_MIN  (-14.0f)
#define RS_T_MAX  ( 14.0f)

static float clamp_f32(float x, float min_v, float max_v)
{
    if (x < min_v) return min_v;
    if (x > max_v) return max_v;
    return x;
}

static uint16_t float_to_u16(float x, float min_v, float max_v)
{
    x = clamp_f32(x, min_v, max_v);
    return (uint16_t)((x - min_v) * 65535.0f / (max_v - min_v));
}

static float u16_to_float(uint16_t raw, float min_v, float max_v)
{
    return ((float)raw) * (max_v - min_v) / 65535.0f + min_v;
}

static uint32_t rs_make_ext_id(uint8_t type, uint16_t data2, uint8_t target_id)
{
    return ((uint32_t)(type & 0x1Fu) << 24)
         | ((uint32_t)data2 << 8)
         | target_id;
}

static void put_u16_be(uint8_t *dst, uint16_t value)
{
    dst[0] = (uint8_t)(value >> 8);
    dst[1] = (uint8_t)value;
}

static uint16_t get_u16_be(const uint8_t *src)
{
    return ((uint16_t)src[0] << 8) | src[1];
}

static void put_f32_le(uint8_t *dst, float value)
{
    uint32_t raw;
    memcpy(&raw, &value, sizeof(raw));
    dst[0] = (uint8_t)(raw >> 0);
    dst[1] = (uint8_t)(raw >> 8);
    dst[2] = (uint8_t)(raw >> 16);
    dst[3] = (uint8_t)(raw >> 24);
}

static float get_f32_le(const uint8_t *src)
{
    uint32_t raw = ((uint32_t)src[0] << 0)
                 | ((uint32_t)src[1] << 8)
                 | ((uint32_t)src[2] << 16)
                 | ((uint32_t)src[3] << 24);
    float value;
    memcpy(&value, &raw, sizeof(value));
    return value;
}
```

### 11.1 构造运控帧

```c
typedef struct {
    uint32_t ext_id;
    uint8_t data[8];
} RsCanFrame;

static RsCanFrame rs_make_motion_frame(
    uint8_t motor_id,
    float p_set,
    float v_set,
    float kp,
    float kd,
    float t_ff)
{
    RsCanFrame frame = {0};

    uint16_t t_raw  = float_to_u16(t_ff,  RS_T_MIN,  RS_T_MAX);
    uint16_t p_raw  = float_to_u16(p_set, RS_P_MIN,  RS_P_MAX);
    uint16_t v_raw  = float_to_u16(v_set, RS_V_MIN,  RS_V_MAX);
    uint16_t kp_raw = float_to_u16(kp,    RS_KP_MIN, RS_KP_MAX);
    uint16_t kd_raw = float_to_u16(kd,    RS_KD_MIN, RS_KD_MAX);

    frame.ext_id = rs_make_ext_id(0x01, t_raw, motor_id);
    put_u16_be(&frame.data[0], p_raw);
    put_u16_be(&frame.data[2], v_raw);
    put_u16_be(&frame.data[4], kp_raw);
    put_u16_be(&frame.data[6], kd_raw);

    return frame;
}
```

### 11.2 构造 float 参数写入帧

```c
static RsCanFrame rs_make_write_float(
    uint8_t motor_id,
    uint8_t master_id,
    uint16_t index,
    float value)
{
    RsCanFrame frame = {0};

    frame.ext_id = rs_make_ext_id(0x12, master_id, motor_id);
    frame.data[0] = (uint8_t)(index >> 0);
    frame.data[1] = (uint8_t)(index >> 8);
    frame.data[2] = 0;
    frame.data[3] = 0;
    put_f32_le(&frame.data[4], value);

    return frame;
}
```

### 11.3 解析类型 2 反馈

```c
typedef struct {
    uint8_t mode_state;
    uint8_t motor_id;
    uint8_t master_id;
    uint8_t uncalibrated;
    uint8_t stall_overload;
    uint8_t encoder_fault;
    uint8_t over_temperature;
    uint8_t phase_current_fault;
    uint8_t under_voltage;
    float position_rad;
    float velocity_rad_s;
    float torque_nm;
    float temperature_c;
} RsMotorFeedback;

static int rs_parse_type2(
    uint32_t ext_id,
    const uint8_t data[8],
    RsMotorFeedback *out)
{
    uint8_t type = (uint8_t)((ext_id >> 24) & 0x1F);
    if (type != 0x02 || out == 0 || data == 0) {
        return -1;
    }

    out->mode_state         = (uint8_t)((ext_id >> 22) & 0x03);
    out->uncalibrated       = (uint8_t)((ext_id >> 21) & 0x01);
    out->stall_overload     = (uint8_t)((ext_id >> 20) & 0x01);
    out->encoder_fault      = (uint8_t)((ext_id >> 19) & 0x01);
    out->over_temperature   = (uint8_t)((ext_id >> 18) & 0x01);
    out->phase_current_fault= (uint8_t)((ext_id >> 17) & 0x01);
    out->under_voltage      = (uint8_t)((ext_id >> 16) & 0x01);
    out->motor_id           = (uint8_t)((ext_id >> 8) & 0xFF);
    out->master_id          = (uint8_t)(ext_id & 0xFF);

    uint16_t p_raw = get_u16_be(&data[0]);
    uint16_t v_raw = get_u16_be(&data[2]);
    uint16_t t_raw = get_u16_be(&data[4]);
    uint16_t temp  = get_u16_be(&data[6]);

    out->position_rad = u16_to_float(p_raw, RS_P_MIN, RS_P_MAX);
    out->velocity_rad_s = u16_to_float(v_raw, RS_V_MIN, RS_V_MAX);
    out->torque_nm = u16_to_float(t_raw, RS_T_MIN, RS_T_MAX);
    out->temperature_c = ((float)temp) / 10.0f;

    return 0;
}
```

## 12. 手册中的矛盾、歧义和固件差异

### 12.1 类型 3 示例代码覆盖主机 ID

RS00 手册第 44 页的 `motor_enable()` 示例中，先把 ID 数据区设置为 `master_id`，随后又写成 `0`，与第 32 页协议表不一致。

按协议表，类型 3 的 bit15~8 应为主机 ID，因此本文采用：

```text
0300FD7F
```

而不是：

```text
0300007F
```

正式接入前建议用官方上位机或 CAN 抓包确认你的固件实际行为。

### 12.2 类型 1 表格中的“Byte2 力矩”表述

手册类型 1 表格把 bit23~8 的 16 位区域描述成“Byte2：力矩”，容易误解。根据 29 位 ID 布局和示例程序，前馈力矩实际位于扩展 ID 的 bit23~8，不在 8 字节 Data 中。

### 12.3 类型 17 应答地址描述

手册的文字列名与示例值存在一定混淆。本文按手册给出的实际应答示例：

```text
11007FFD
```

解析为：

```text
bit23~16 = 成功/失败标志
bit15~8  = 电机 ID
bit7~0   = 主机 ID
```

### 12.4 类型 21 ID 表格方向可能有歧义

类型 21 的表格中示例值和“电机 ID/主机 ID”的文字排列不够清晰。故障判断应以 Data 中的 fault/warning 和实机抓包为准，不应只根据该表格的一行地址描述推断所有固件行为。

### 12.5 类型 24 应答随固件变化

手册明确写出 `0.0.3.2` 前后存在差异，接收代码应兼容类型 2 和类型 24 两种应答。

## 12.6 功能版本要求

手册标注：

- 类型 22、23、24：`0.0.3.0` 及以后采用该协议。
- 主动上报应答：`0.0.3.2` 前后不同。
- 位置映射范围在较早固件中曾使用 `12.5`，后续改为 `12.57`。

因此，协议程序最好先读取版本号，再决定兼容策略。

### 电机使能

```text
发送成功  ID 0x0300FD7F  Data 00 00 00 00 00 00 00 00
接收成功  ID 以类型 2 开头，例如 0x02807FFD
          Data = 位置、速度、力矩、温度
```

### 参数读取

```text
发送成功  ID 0x1100FD7F  Data [index_L index_H 00 00 00 00 00 00]
接收成功  ID 以类型 17 开头
          Data Byte0-1=返回 index，Byte4-7=参数值
```

看到这三种记录时，先判断“通信类型是否符合预期”，再解析具体数值。
